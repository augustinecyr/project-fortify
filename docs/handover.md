# Handover Guide — Project Fortify v1.0

## Architecture overview

```
                        ┌─────────────────────────────────────┐
                        │          fortify-network (bridge)   │
                        │                                     │
  Browser               │  ┌─────────────┐                   │
  :8501 ───────────────►│  │  frontend   │  Streamlit         │
                        │  │ :8501       │  dashboard         │
                        │  └──────┬──────┘                   │
                        │         │ HTTP (internal)           │
                        │         ▼                           │
                        │  ┌─────────────┐                   │
  API client            │  │    api      │  FastAPI + uvicorn │
  :8000 ───────────────►│  │ :8000       │  JWT auth          │
                        │  └──────┬──────┘  rate limiting    │
                        │         │                           │
                        │    ┌────┴────┐                      │
                        │    ▼         ▼                      │
                        │  ┌──────┐  ┌──────┐                │
                        │  │  db  │  │cache │  PostgreSQL 15  │
                        │  │ :5432│  │ :6379│  Redis 7       │
                        │  └──────┘  └──────┘                │
                        └─────────────────────────────────────┘
```

All four services run inside a single Docker bridge network (`fortify-network`). The browser and any external API clients reach the stack via the two published ports (8501 and 8000). Internal service-to-service traffic stays on the bridge and never leaves the host.

## Credential rotation

### JWT Secret Key (`SECRET_KEY`)

Rotating this key immediately invalidates all active sessions — every logged-in user will be signed out.

1. Generate a new secret: `python -c "import secrets; print(secrets.token_hex(32))"`
2. Update `SECRET_KEY` in `.env`.
3. Restart the API: `docker compose up -d api`

### Database password (`POSTGRES_PASSWORD`)

1. Update `POSTGRES_PASSWORD` in `.env`.
2. Update the password inside the running container:
   ```powershell
   docker exec -it fortify-postgres psql -U fortify_user -d postgres -c "ALTER USER fortify_user PASSWORD 'new-password';"
   ```
3. Restart the API so it picks up the new `DATABASE_URL`: `docker compose up -d api`

### Groq API key (`GROQ_API_KEY`)

1. Revoke the old key at `console.groq.com/keys`.
2. Create a new key and update `.env`.
3. Restart the API: `docker compose up -d api`

### Groq model (`GROQ_MODEL`)

Groq deprecates hosted models periodically. If AI Insights starts returning
fallbacks and the API logs show a model-not-found error, set `GROQ_MODEL` in
`.env` to a current production model and restart the API — no code change
needed.

### Admin user password

The admin user is seeded by `data/seeds/seed_users.py`. To change the password:

```powershell
docker exec -it fortify-postgres psql -U fortify_user -d fortify
```
```sql
UPDATE users SET hashed_password = '<bcrypt-hash>' WHERE username = 'admin';
```

Generate a bcrypt hash:
```powershell
docker exec fortify-api python -c "from app.auth.security import get_password_hash; print(get_password_hash('new-password'))"
```

## Known limitations (Phase 1)

These are by-design constraints accepted for the v1.0 scope:

| Limitation | Detail |
|---|---|
| Single admin user | Only one user account (`admin`) is seeded. There is no self-service user registration. |
| No automated remediation | The platform is read-only and advisory. No action is taken on VMs automatically. |
| No multi-tenancy | All authenticated users see the full VM fleet. There is no per-team data isolation. |
| Simulated VM data | The VM fleet is generated by `data/generators/metrics_simulator.py`. There is no real hypervisor integration. |
| No production SLA | The stack has no high-availability configuration. A single Docker host with no replication is assumed. |
| JWT stored in browser cookie | The cookie is not `HttpOnly` because Streamlit's component model requires JavaScript access. The token TTL is 30 minutes. |

## Deferred to Phase 2

From `docs/scope-definition.md`:

- **Automated remediation** — trigger actions against VMs via hypervisor or cloud APIs based on detected anomalies.
- **Multi-tenant isolation** — per-team or per-customer data separation with RBAC.
- **Production SLA** — active/passive failover, replicated database, load-balanced API.
- **Cost optimisation recommendations** — cloud spend analysis and rightsizing suggestions.
- **Extended security analytics** — CVE correlation, vulnerability scoring, patch management integration.
- **Real hypervisor integration** — replace the simulator with vSphere, AWS, or Azure data sources.
